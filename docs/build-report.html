02

Three surfaces, one pipeline

The whole design

Everything you touch is one of three things, and each exists because the other two cannot do its job. The split is the whole design — once it is clear, every feature in this document explains itself.

Telegram — every decision

Live

Capture, the interview, approving, scheduling, verdicts, clearing a name, adding a rule. Anything answerable with a tap, wherever you already are. Nothing here needs a laptop.

The desk — every prose job

Live

Editing a post, writing the library, finding a moment, rolling a change back, exporting everything. Four jobs a chat box physically cannot do, because each needs a cursor.

The reader — one input

Not installed

Runs on your own laptop, reads your Claude Code sessions, sends a short digest. Set up once, then silent. The only piece that needs software on your machine.

Underneath all three

One database and ten background services on nine schedules — the queue every minute, selection every four hours, publishing every five minutes, a check each morning at eight, the learning run on Monday. It mines, scores, drafts, checks and reports without anyone starting it.

Why the split is drawn there

Your specification says the weekly pass must happen where you already are, because "a separate habit will not survive". So every decision is in Telegram.

It also says the idea bank must be editable "without going through the chat interface". So the four jobs needing a keyboard get a screen — and nothing else does.

The rule of thumb

Answerable with a tap → Telegram.
Needs a cursor → the desk.

That is why the desk is only six screens. It is not a second copy of the bot; it is the small residue of work that genuinely needs a keyboard.

What it actually sends, and why --doctor exists

A short digest of what you said and decided. Never code, never client material. Of 576 files on a typical machine, 535 are discarded before anything is read, and only the genuinely unusual sessions survive after that.

A wrong key produces silence — and a week that produces nothing is a legitimate pass here, so a broken setup and a quiet week look identical from outside. Checking the credentials against the real server is the only way to tell them apart.

04

What else was built

The part you never see

Most of the work is not a feature. It is the machinery that keeps the features honest when nobody is watching — and it is the majority of what was built. This section exists because none of it appears anywhere else in this document.

A database that refuses bad states

Proven

28 tables, 73 access rules, 31 constraints. No delete permission exists anywhere, so nothing you have said can be destroyed by any code path — only killed and labelled. Every table is behind row-level access, so a query cannot return material you are not entitled to even if the code asks for it.

A queue that survives failure

Proven

Every piece of work is a job. A job that dies half-way becomes claimable again rather than being lost, retries back off rather than hammering, and a genuine failure is separated from a temporary one — a rate limit gets forty patient attempts, a real error gets five. This is why a dropped connection at 3am does not cost you a voice note.

The retelling check

Proven

Every published post is indexed by meaning, not by words, so the system can tell that a new draft is the same story told differently. The thresholds were measured against your material rather than guessed — and when they were inherited from elsewhere they would have blocked nothing while appearing to work.

It notices its own drift

Proven

The system records every outside service it actually calls and tells you the first time it uses one that is not on your list. A test also fails the build if the tool list you hold and the list the system checks itself against ever disagree. Both exist because that drift already happened once.

95 automated tests, and four measuring harnesses

Proven

The tests pin the things that would fail silently: that your own underscores and asterisks survive formatting, that an unmeasured acceptance test reports as unmeasurable rather than as zero, that every button offered maps to an action. The harnesses measure the system against your own acceptance criteria and can be re-run at any time — the scorecard in section 07 is generated, not typed.

Six documents, and a rehearsed handover

Proven

The specification read clause by clause, the seven build decisions with their reasoning, the running cost, an operating runbook, the sequence for moving everything into your accounts, and the running order for the recorded walkthrough. The account move is rehearsed rather than described: all 27 database migrations were applied to an empty database to prove the sequence works before anyone depends on it.

Why this matters more than it sounds

Four times during this build a control was found that looked like it worked and did nothing — a button that reverted a post and recorded no reason, a rollback that silently matched no rows, a skip that was never read, a scheduler entry nobody ever created. Each was found by driving the live system rather than by reading the code. The machinery above is what makes the next one visible.

How a post actually gets made

Nine steps

The order is fixed and every step can stop. Nothing skips ahead — in particular nothing is ever drafted from a transcript or a session log without interviewing you about it first, because a recording captures what was said and not what you made of it.

#StepWhoWhat happens
01Something arrivesYouA voice note, a typed thought, a call transcript, a Claude Code session, or a Slack thread if you turn it on. All five land in the same idea bank.
02It asks you about itAutomaticUntil the moment has a scene, a detail and a realisation. Then it stops. If it cannot get there, the moment parks rather than being padded out.
03It picks what to writeAutomaticScored on five factors, balanced across your pillars, checked against everything published so a story is never retold. If the bar cannot be met it writes fewer and says why.
04It writes a draftAutomaticReading only your bank entry and your library. It never browses and never researches, and it emits every factual claim with its source text beside it.
05Eight checksAutomaticCould anyone else have written this · does every claim trace to something you said · is a client identifiable · are all names cleared · does it sound like you · does the hook earn the next line · is it aimed at someone · does it use banned phrasing. Each can reject on its own.
06It reaches your calendarAutomaticAs a draft, never live, with its image attached if you sent one.
07You approve itYouA tap in Telegram or an edit in the calendar. This is the only thing that authorises publishing, and the database refuses to store a published post without it.
08It publishesAutomaticTo LinkedIn, on the date you set. Never before, and never anything you did not approve.
09It learnsAutomaticWhat it wrote against what you approved, the numbers after seven days, and one question a week about whether a post started a conversation. It proposes library changes with evidence; you decide.
06

The three rules it cannot break

Held by the database

Not policies the code tries to follow — constraints the database will not let it violate, which means they hold even if the code above them is wrong.

RuleHow it is held
Only you could have written itKept in a locked section of your library. The learning loop is structurally unable to propose a change to it — a database rule rejects the attempt.
Nothing inventedEvery claim carries its source text and is verified mechanically, before any model gives an opinion. Missing detail stays missing, and the draft works without it.
Nothing publishes without youFour constraints make an unauthorised published post impossible to store. Tested by trying: the database refuses all three ways of doing it.
And one thing that is never tunable

The learning loop can change how it writes — hooks, structure, pillars, timing. It can never loosen the two rules above, whatever the engagement numbers say. A system optimising freely against LinkedIn engagement finds its way to engagement bait, and that is the one outcome that would make the whole thing worthless.

The one thing that unblocks the most

A model good enough to write and to judge. The build has been running on free tiers, which allow 8,000 words a minute where a single quality check needs roughly 16,000. That one fact blocks four component tests and the finish line itself.

The intended route is Claude Code rather than buying API credits — you already have it, and there is already a small agent running on your machine on a schedule that could carry the drafting and the checks. This is not built yet. It is the next substantial piece of work, and it is what those four rows are waiting on.

Worth being precise about what this is not: the gate is not broken. Reading its rejections shows it correctly catching genuine invention — phrases the free model added that you never said. The safety mechanism works; the writer beneath it is the cheap one.

What comes next

Planned, not built

Two pieces of work are already scoped. Neither is in your specification, and neither is built — they are here so nothing arrives as a surprise.

Drafting and checking through Claude Code

Planned

Instead of buying model credits, the drafting and the eight checks would run through the Claude Code subscription you already have, driven by the same local agent that already reads your sessions on a schedule. This is what unblocks four of the twelve acceptance tests and the finish line, and it is the next substantial piece of work.

A connector for the system itself

Planned

A small server that lets Claude Code — or any similar tool — read the idea bank, check where things stand and run the system directly, without opening the app or the database. Useful for you and for whoever maintains this after handover, and the natural companion to the item above.
